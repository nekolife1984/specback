# PRレビュープロセス

## 概要

ソースコード・テスト・機能変更は必ず Pull Request を経由します。すべての変更がレビューされ、CIが通過し、ドキュメントが同期されることを保証します。

## PRライフサイクル

```
1. mainからブランチ → 2. 変更 → 3. Push → 4. PR作成
                                               ↓
                                       CI自動実行
                                               ↓
                                   5. レビュー（自分or他者）
                                               ↓
                                   6. Squash merge → main
                                               ↓
                                   7. ブランチ削除
```

## PRテンプレートの埋め方

リポジトリには `.github/pull_request_template.md` が用意されています。各セクションの埋め方：

### 概要
変更内容と**理由**を記載します。「この変更は何を解決するのか」が伝わるように。

### 変更の種類
該当するものにチェック：

- `feat:` — 新機能・機能拡張
- `fix:` — バグ修正
- `chore:` — CI・リファクタリング・メンテナンス・依存関係
- `docs:` — ドキュメントのみ
### チェックリスト
各項目を確認してからチェック：

| 項目 | 理由 |
|------|------|
| ブランチ名が命名規則に従っている | 履歴のナビゲーション |
| 1ブランチ = 1論理変更 | クリーンなsquash merge |
| `pytest tests/ -q` が通る | CIゲート |
| `pyrefly check scripts/` が通る（該当時） | CIゲート（ブロッキング） |
| Trace/drift gate が通る（該当時） | 仕様の整合性 |
| `CHANGELOG.md` を更新した | リリース準備 |
| ドキュメント（EN + JA）を更新した | バイリンガル一貫性 |

### 関連Issue
- `Closes #N` — マージ時に自動クローズ
- `refs #N` — 参照のみ（クローズしない）

## レビュアーチェックリスト

自分自身のPR、他者のPRの両方で確認：

### 機能面
- [ ] 変更内容は主張通りに動作するか？
- [ ] エッジケースが漏れていないか？
- [ ] 既存の動作を壊していないか？

### テスト
- [ ] 新規スクリプトに対応するテストファイルがあるか？
- [ ] 既存のテストは通るか？
- [ ] テストのアサーションは意味があるか？

### ドキュメント
- [ ] ENドキュメントは更新されたか？
- [ ] JAドキュメントは更新されたか？
- [ ] READMEに影響があるか？更新されたか？
- [ ] AGENTS.md / CONTRIBUTING.md に影響があるか？更新されたか？
- [ ] CHANGELOG.md は更新されたか？

### i18n 整合性
- [ ] EN版とJA版の内容が一致しているか？（翻訳のずれがないか）
- [ ] 技術用語（ブランチ名、CLIフラグ、ファイルパス）が両言語で一致しているか？

## Squash Merge

このプロジェクトは **squash merge** のみを使用します。PRのタイトルが `main` 上のコミットメッセージになります。

> **PRタイトルを良い conventional commit メッセージにしてください。**
> 例: `feat: add Flask extraction guide (#42)`

マージ後はブランチを削除：

```bash
git checkout main
git branch -D feat/your-branch        # ローカル
git push origin --delete feat/your-branch  # リモート
```

## CIが失敗したら

1. どのステップが失敗したか確認（CIチェックの "Details" をクリック）
2. ローカルで修正
3. コミット＆push — CIが自動再実行
4. すべて通るまで繰り返し

CIは `cancel-in-progress` 設定のため、新しいコミットをpushすると前回の実行は自動キャンセルされます。

## 緊急バイパス

```bash
git commit --no-verify              # pre-commit hookをスキップ
git push --no-verify origin main    # pre-push hookをスキップ
```

真の緊急時にのみ使用（main破壊、緊急ホットフィックス）。事後的に正規のPRを作成してください。

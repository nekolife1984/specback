# Drift Detection CI

> **Documentation**: [English](05-drift-ci.md) · [日本語](../ja/05-drift-ci.md)

## Overview

specback generates a spec that starts drifting from the code the moment it is
generated. The drift detection machinery (`detect-drift.py`, `gates.py`,
`git_utils.py`) was previously manual-only (Phase 7), so in practice nobody
ran it regularly — the "honest spec" silently decayed into a "beautiful
fiction" within weeks.

This document describes the **CI automation** (Issue #266) that connects the
existing drift assets to the daily development flow:

- A GitHub Action (`specback-drift`) that runs on every PR
- A thin wrapper (`scripts/specback-gate.py`) that also works locally
  (`--ci` mode — same behaviour without `act`)
- An opt-in pre-push hook (`scripts/install-drift-hooks.sh`, warn mode by
  default)

## How it works

The wrapper chains the existing verification scripts:

```text
git merge-base(origin/<base>, HEAD)
        │
        ▼
detect-drift.py --base <merge-base> --json
        │                       │
        │                 drift-report.md / drift-report.json
        ▼
fix-refs.py --check            (orphaned REF detection — warning only)
        │
        ▼
drift-report sanity            (equivalent to gates.py --gate drift_detected)
        │
        ▼
verdict: pass / warn / fail
```

### Warn/fail 2-stage policy

| Verdict | Exit | Meaning |
|---------|------|---------|
| **fail** | 1 | `drift-report.json` reports affected spec sections or deleted sources with refs. The spec must be updated in this PR. |
| **warn** | 0 | No fail-level drift, but orphaned REFs or new uncovered sources were found. Reported without gating. |
| **pass** | 0 | No drift, no warnings. |

### Base resolution (merge-base)

In CI, the diff base is the **merge-base** of the PR branch against the base
branch — not `generated_at_commit` from `state.json` (which is a snapshot from
generation time and would report every subsequent commit as drift).

Resolution priority:

1. Explicit `--base` CLI argument
2. CI mode (`--ci`): `GITHUB_BASE_REF` → `origin/<base>` merge-base, then
   `origin/main` merge-base
3. Local default: `origin/main` merge-base
4. `HEAD` (last resort)

All refs pass through `git_utils.resolve_ref()` (SAFE_REF_RE + rev-parse),
so git option injection via `--base` is rejected (Issue #253 hardening).

### Spec-not-generated skip

A project that has not run specback yet has no `source-map.json` /
`trace.json`. In that case the gate returns **warn** (exit 0) with the message
"spec artifacts missing — run specback to generate the spec first". The drift
gate only applies once a spec has been generated, so enabling the workflow on
a fresh repo does not break CI.

### fix-refs failure handling

The `fix-refs.py --check --json` step is warning-only, but its output
contract is enforced: if fix-refs exits non-zero or its stdout is not the
expected JSON (e.g. a future contract change), the gate does **not** silently
report "0 orphaned / ok". Instead it records a warning and sets
`fix_refs.ok = false` in the JSON output so a broken integration is visible
rather than a false pass (Issue #313).

## GitHub Action

### Using in your project

Copy `templates/ci/specback-drift.yml.example` to
`.github/workflows/specback-drift.yml` and adjust:

```yaml
- uses: nekolife1984/specback/.github/actions/specback-drift@main
  with:
    specback-dir: .specback      # path to .specback/
    fail-on-drift: "false"       # "true" to fail the build on drift
    comment-on-pr: "true"        # post a summary comment on the PR
```

Requirements:

- **`fetch-depth: 0`** in the checkout step — full history is needed to
  resolve the merge-base.
- `permissions.pull-requests: write` on the job — needed to post the PR
  comment.
- The action resolves `origin/<base>` from `GITHUB_BASE_REF`; the base
  branch must be fetched (default checkout of a PR does this for the
  merge-base commit).

The action runs `specback-gate.py --ci`, then posts a comment like:

```markdown
## 🤖 specback drift check
**Status: 🔴 FAIL — the spec is affected by this PR.**

- **Changed files**: 3
- **Affected spec sections**: 2
- **New uncovered sources**: 1
- **Deleted sources with refs**: 0
```

### PR comment generation

The comment body is generated by
`.github/actions/specback-drift/post-comment.py`. It skips the comment when
there is nothing to report (no changes, pass verdict). The comment is posted
with `gh pr comment` using the provided token.

**Fork PRs**: comments are skipped on pull requests from forks. The default
`GITHUB_TOKEN` on fork PRs only has `pull-requests: read`, so `gh pr comment`
would fail with `Resource not accessible by integration (addComment)` — the
action detects the fork (`head.repo.full_name != github.repository`) and
skips the comment step instead of failing the job (#339).

## Local validation mode (`--ci`)

The same behaviour can be reproduced locally without `act`:

```bash
# CI mode: resolves merge-base from GITHUB_BASE_REF or origin/main
python scripts/specback-gate.py --ci --specback-dir .specback --json

# Explicit base
python scripts/specback-gate.py --base origin/main --specback-dir .specback --json

# Pre-push style: never block, only warn
python scripts/specback-gate.py --ci --warn-only --specback-dir .specback
```

Exit codes: `0` = pass/warn, `1` = fail (drift), `2` = usage/environment error.

## Opt-in pre-push hook

For projects that want drift detection without GitHub Actions (or in addition
to it), an opt-in pre-push hook is provided. **Default is warn mode** — the
hook detects drift but does not block the push.

```bash
# from the target project root
sh /path/to/specback/scripts/install-drift-hooks.sh

# fail mode (blocks push on drift)
SPECBACK_FAIL_ON_DRIFT=1 sh /path/to/specback/scripts/install-drift-hooks.sh
```

What it does:

- Installs a generated `.git/hooks/pre-push` that chains any existing
  pre-push hook (backed up to `pre-push.specback-backup`).
- Runs `specback-gate.py --ci` (warn mode) or `--warn-only` logic on each
  push.
- Uninstall: `rm .git/hooks/pre-push && mv .git/hooks/pre-push.specback-backup .git/hooks/pre-push`.

## Other CI systems

A GitLab CI example is provided in
`templates/ci/specback-drift.gitlab-ci.yml.example`. It runs the same
`specback-gate.py --ci` on merge request pipelines and keeps
`drift-report.md/json` as artifacts.

## Dogfooding

The specback repository itself runs this workflow
(`.github/workflows/specback-drift.yml`, `fail-on-drift: "false"`). Because
the specback repo does not (yet) have a full `.specback/` self-generation,
the gate reports **warn** ("spec artifacts missing") on its PRs — which also
serves as a live check that the action wiring is intact.
